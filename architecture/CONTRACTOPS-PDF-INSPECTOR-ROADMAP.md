# ContractOps × PDF Inspector 后续开发方案

> 2026-10-09 实现进展：已交付统一工作台、知识库管理、文档详情/不可变版本，以及管理知识库的 PDF Inspector 任务适配、质量结果和原件来源页预览；新增 5–8 项合同关联、规则候选核对、预审和人工审批本地闭环，并提供可选带引用模型客户端（当前未配置真实模型）。DOCX 保留基础解析，OCR 当前未启用；任务由页面轮询/手动同步写回，不是常驻业务 Worker。Inspector 合同专用提取模板和正式 PG 集成验证尚未完成。当前可运行范围见 [知识库 MVP](CONTRACTOPS-KNOWLEDGE-MVP.md) 与 [工作台 MVP](CONTRACTOPS-WORKBENCH-MVP.md)。下文描述目标方案，不代表全部已实现。

## 1. 项目定位

将 ContractOps 定位为“带文档预审助手的合同审批与履约管理后端”，将 PDF Inspector 作为可复用的文档处理引擎。

本方案结合了“突出多租户隔离、读写一致性，以后端项目为主”的建议，以及审批人希望由助手提前阅读合同的场景。首版用于本地运行与面试展示，以真实业务流程和异常恢复为交付依据。

两个项目分别保留仓库和职责：

| 项目 | 负责内容 |
| --- | --- |
| PDF Inspector | PDF 分类、版面/表格提取、可选本地 OCR、模板字段候选、来源引用和文档质量提示 |
| ContractOps | 租户与角色权限、合同版本、候选值确认、预审报告、审批状态机、履约义务、可靠事件和业务审计 |

ContractOps 是业务事实源。PDF Inspector 返回的候选字段和模型建议不能直接修改合同台账，也不能自动批准合同或创建正式履约义务。

## 2. 当前基础与新增范围

截至本方案编写，ContractOps 已有文档上传、文档 Worker、基础 PDF/DOCX 解析、金额日期提示、版本 Diff、顺序审批、履约调度、RLS 隔离及审计。

PDF Inspector 已提供本地任务服务、结构化结果、证据块、可选 RapidOCR 和提取模板。其本地后端按单实例组织任务，不能因为提供 API 角色权限就认为已经具备 ContractOps 的租户隔离能力。

以下是目标范围及当前进展：

- PDF Inspector 任务适配器与结果映射：已用于管理知识库；业务合同 Worker 尚未接入。
- 合同专用提取模板、质量状态和人工确认接口。
- 围绕审批任务生成的预审报告及异步刷新机制。
- 贯穿两项目的集成测试和可重复本地演示：知识库上传、状态、原件页面已经本地实测；完整审批链与真实数据库故障测试待补。

最小版本不扩展通用 OA，不建设可视化工作流编辑器，也不引入并行会签、多 Agent 或 Kubernetes。知识库默认检索与原文摘录问答，可选模型语义组织；审批沿用现有可配置顺序流程；真实模型效果与模型路由保留为后续实验。预审目前按用户操作生成，不是异步审批事件自动刷新。

## 3. 最终业务流程

1. 经办人创建合同，并上传独立文件版本。
2. ContractOps 文档 Worker 校验文件摘要，提交 PDF Inspector 任务。
3. PDF Inspector 提取正文、表格及字段候选，必要时执行本地 OCR。
4. ContractOps 保存来源证据、提取质量和字段候选；经办人核对并确认业务字段。
5. 合同提交审批，系统匹配策略并生成审批任务。
6. 已就绪的审批任务异步生成预审报告；审批人查看摘要、核查项和原文证据。
7. 审批人选择通过、驳回或退回修改，可附自然语言意见。
8. 审批通过后，授权人员激活合同，并确认付款、交付等履约义务。
9. Scheduler 执行到期检查，提醒和风险处置均保留审计记录。

首版 PDF 走 Inspector 适配器，DOCX 保留现有解析路径，两者输出同一套业务证据格式。暂不把 DOCX 转 PDF 作为前置条件。

## 4. 文档联动设计

### 4.1 接入方式

优先通过本地 HTTP 接口接入 PDF Inspector。这样可复用其 OCR、任务持久化及进程资源限制，也避免让 ContractOps API 进程直接承担 Rust/OCR 运行依赖。

复用的 Inspector 接口包括：

- `POST /v1/tasks`：提交 PDF 与提取模板。
- `GET /v1/tasks/{id}`：查询任务状态。
- `GET /v1/tasks/{id}/result`：获取结构化结果。
- `GET /v1/tasks/{id}/chunks`：读取证据块。

调用发生在文档 Worker 内，不阻塞用户上传请求。Inspector 地址与服务密钥由可信部署配置指定；浏览器只访问 ContractOps，不直接查询 Inspector 的任务列表或结果。

### 4.2 任务与结果身份

新增集成任务记录，关联 `tenant_id`、`contract_version_id`、文件 SHA-256、提取模板版本、解析器版本和外部任务 ID。

- 外部任务 ID 不是访问凭证，所有读取先经过 ContractOps 的资源权限检查。
- 使用租户与合同版本范围内的唯一约束，避免重复领取产生重复业务证据。
- Worker 重启后继续轮询已记录的外部任务，不重新提交全部文件。
- 提交外部任务后若响应丢失，记录为“外部提交结果未知”，再进行核对或受控重试。现有接口不能直接假定支持幂等创建；必要时为 Inspector 增加接入方请求键。
- 外部重复任务与本地重复业务写入分别处理，不宣称跨进程调用天然只发生一次。

结果写回继续使用 ContractOps 租约校验和事务，旧任务结果不得覆盖新版本或被接管后的处理结果。

### 4.3 统一证据与质量状态

保存正文证据及其页码、章节、来源类型、外部引用和解析版本。Inspector 的证据块可能合并多页来源，不能只取第一页丢弃其余引用；必要时新增证据来源关联表。

保留原生提取、OCR、原生加 OCR 等来源差异，以及相关置信度和质量问题。字段候选引用原文证据；如果规则生成了规范化值，则同时保存原始值和转换规则。

文件处理状态与质量状态分开建模：

- 处理状态说明任务是否运行、完成或失败。
- 质量状态说明结果是否需要人工复核、缺页或存在字段冲突。

Inspector 的 `ready` 仅代表其已实现检查未要求复核；`needs_review` 必须保留。空正文、未完成 OCR 和质量告警不能被静默视为可供完整预审的合同。

### 4.4 合同模板与人工确认

新增合同模板，先覆盖交易方、总金额、币种及明确的付款/交付日期。模板按版本固定，使用经过标注的合同样本验证，不能直接套用已有报价或发票模板后宣称完成。

优先做两类确定性核查：

1. 候选金额、币种或交易方与台账字段不一致。
2. 当前模板要求的字段没有提取到，或同一字段出现多个冲突候选。

没有提取到字段，应描述为“当前证据未定位到，需人工核对”，不能断言原合同没有该条款。

新增候选确认接口，使用权限校验、`expected_version`、幂等键和同一数据库事务保存确认与台账变更。候选金额或日期不自动成为合同金额或正式义务。

首版新联动流程在提交审批前要求完成关键字段确认；同时明确现有接口的迁移规则，避免旧合同被新增条件无解释地阻断。文档质量问题由明确的人工复核记录处理，不允许以后台直接改表绕过。

## 5. 审批预审助手

### 5.1 对审批人的输出

助手是一项受控的异步分析功能，不是拥有审批权限的个人代理。首版报告包含：

| 内容 | 示例或含义 |
| --- | --- |
| 合同摘要 | 本次签约对象、金额、期限与主要事项 |
| 确定性核查 | 台账金额与文件候选金额不一致、当前审批步骤的金额门槛 |
| 待关注问题 | 付款安排、交付期限、责任条款等需要核对的内容 |
| 原文证据 | 合同版本、证据块、来源页码及可核对原文 |
| 阅读限制 | 未识别页面、OCR 告警、模型失败、输入被截断 |
| 人工处理 | 标记已核对、误报或待补充，并留下处理意见 |

规则核查与模型推测分开展示。报告可提供“需核对”“建议补充资料”等阅读建议，不把模型建议转换成系统审批决定。

### 5.2 触发、版本和权限

合同提交审批的事务中记录预审事件，由后台任务生成报告。任务与审批实例、审批步骤、合同文件版本、台账状态版本、核查规则版本和模型配置版本关联。

- 审批任务进入可处理状态时，可以复用完全相同输入的报告；不因每次打开页面都重复调用模型。
- 台账字段修订、文件更新或核查规则变化后，旧报告标为过期，不能显示为当前结果。
- 保存生成所用的输入快照摘要；报告完成前再次核对版本，防止读取旧数据后写成新报告。
- 报告、证据和人工处理记录遵守现有租户、部门与角色权限。转交后重新校验任务访问权限。
- 报告就绪通过 API 状态查询体现，不依赖“写入后睡几秒”假定一致性。

### 5.3 模型边界与降级

首版复用一个明确配置的模型，优先完成证据约束和异常处理，不同时建设多模型路由。

模型无审批写权限。输出经过结构校验和证据引用检查；引用必须属于本租户、本次输入中的合同版本，原文片段必须匹配提供的证据。引用匹配只能证明来源存在，不能保证法律推断正确。

合同正文作为待分析数据处理，不能使模型越权执行工具或更改系统规则。模型请求采用受控输入大小、超时、并发限制和调用预算，记录模型标识、版本及耗时，不把密钥或原文写入普通日志。

模型关闭、超时或输出不合法时，保留规则核查报告，并明确显示模型部分不可用；不把失败伪装成“没有风险”。审批人可以在满足既定人工复核条件后继续审批，AI 可用性不成为审批服务的单点依赖。

## 6. 后端工程重点

| 重点 | 本次联动需要证明的行为 |
| --- | --- |
| 多租户隔离 | 修改合同、报告或外部任务 ID，不能取得另一租户的内容；权限正确的正向读取仍成功 |
| 读写一致性 | 字段确认、版本更新、预审读取同时发生时，不出现新合同配旧报告 |
| 幂等与并发 | 重复点击确认、重复消费事件或重复领取任务，不产生重复业务变更 |
| 异步恢复 | Inspector 或 Worker 重启后可恢复；超时、结果未知和失败重试有明确状态 |
| 证据完整性 | 页码、多来源引用、提取质量和输入截断信息不会在适配中丢失 |
| 业务闭环 | 人工审批与履约调度沿用确定性状态机，可通过审计重建处理过程 |

不在 PDF Inspector 内再复制一套合同审批和履约数据库。Inspector 保持单实例本地文档服务，ContractOps 负责业务任务的编排与结果授权。

## 7. 分阶段交付

### 阶段一：先接通文档引擎

交付任务适配器、状态映射、任务关联、证据映射和配置开关。先用文字型 PDF 接通，再使用已准备 OCR 依赖的扫描件验证；DOCX 路径保持可运行。

通过标准：一份 PDF 从 ContractOps 上传后，在 Inspector 完成处理，证据可通过 ContractOps 按权限读取；重复执行、服务重启及外部超时不会重复写入证据或错误地报告成功。

### 阶段二：加入合同字段确认

交付合同模板、字段候选、质量提示、人工确认 API、确认审计和提交前约束。

通过标准：台账金额与文档金额冲突能够展示双方证据；人工确认后按事务更新台账；陈旧确认被拒绝，重复确认可重放，未完成复核不能绕过新流程门禁。

### 阶段三：加入审批预审助手

先交付纯规则报告，再增加可选模型摘要与疑点分析。实现报告任务、版本绑定、过期判断、证据校验和人工核查记录。

通过标准：审批人看到当前版本报告；报告带原文来源；修改文件或字段后旧报告失效；关闭模型仍能完成规则核查与人工审批。模型既不能修改业务字段，也不能执行审批。

### 阶段四：完成本地演示与面试材料

提供固定演示样本、角色与测试租户初始化、启动检查、自动化闭环脚本和脱敏结果报告。演示界面只需一个薄页面或接口演示工具，优先完成业务链路，不改造整个 OpenMAIC 前端。

通过标准：在本机重复执行上传、解析、字段确认、预审、审批、履约和审计；另外演示跨租户拒绝、并发确认冲突、后台恢复和模型降级。

按个人开发安排，可将四阶段分别规划为约一周的迭代；这是工作拆分参考，不是承诺工期。第一阶段实跑后再根据环境安装、合同样本和 OCR 效果调整后续计划。

## 8. 面试演示案例

准备文字合同、扫描合同和一份修改金额的合同，均使用虚构企业数据。

1. 创建台账金额 20 万元，上传原文金额 25 万元的合同。
2. 查看 Inspector 解析结果和金额冲突，核对原文后确认台账修订。
3. 提交审批，查看预审报告中的付款、交付条款和待关注问题。
4. 演示法务领取与转交，完成需要的财务审批。
5. 激活合同，人工登记付款义务，展示到期提醒与审计。
6. 在另一个可修订的合同中上传新版本，证明旧预审报告不会沿用。
7. 使用租户 B 请求租户 A 的报告，展示访问拒绝；再读取 B 自己的数据作为对照。
8. 中断一个文档任务再恢复，并关闭模型展示降级流程。

演示重点是文档理解如何变成可确认、可审批、可追溯的业务事实，不声称系统能自动判断合同法律效力。

## 9. 后续增强顺序

完成上述闭环后，再根据面试方向选择一个增强项：

- 偏后端：完善企业用户目录、转交目标校验与审批任务分配。
- 偏 AI 应用：接入经过人工维护的制度版本，增加有来源的制度核查与效果评测。
- 偏平台工程：接入 Switchyard，比较固定模型与路由模型在同一标注数据上的质量、耗时和实际成本。

知识库检索若后续加入，必须先解决租户授权和版本范围；模型建议触发复杂审批分支或自动处置不纳入首版。
