# ContractOps：企业合同审批与履约风险管理系统

> 我开发的一个以企业合同管理为业务背景的后端工程项目，重点实现多租户隔离、条件审批、可靠异步处理和履约风险追踪。目前用于本地演示与技术面试，不以真实企业上线运营为项目成果。

## 一、项目简介

ContractOps 不只是一个上传和查看合同文件的工具，而是围绕合同从建档、版本管理、审批到履约跟踪的业务后端系统。

我希望通过这个项目回答几个实际问题：

- 一份合同应该由谁审批，不同金额和部门是否需要不同审批流程？
- 多个人同时操作同一条审批任务，如何避免状态被相互覆盖？
- 合同通过审批以后，付款、交付和续约等事项如何持续跟进？
- 通知服务或后台进程发生故障时，已经提交的业务操作如何恢复处理？
- 多家企业共用一个系统时，如何避免数据串租户，并保留可追溯的操作记录？

项目主线是：

**合同建档 → 文件上传与解析 → 条件审批 → 合同激活 → 履约跟踪与风险提醒 → 审计追溯。**

本文聚焦仓库中的 ContractOps 业务后端及配套部署、测试代码，不将仓库内其他应用视为本项目已经完成的合同管理前端。

## 二、项目背景与业务场景

我以企业采购和服务合同作为主要建模场景，将经办人、法务、财务和审计人员的协作过程抽象为可执行的业务规则。

例如，一份办公设备采购合同可以这样流转：

1. 经办人创建合同，填写交易方、金额、币种和所属部门。
2. 上传合同文件，系统保存独立版本，后台解析正文并提取金额、日期等证据。
3. 提交审批，根据合同类型、部门和金额匹配审批策略。
4. 法务进行审核；对于达到指定金额的合同，再进入财务审批步骤。
5. 审批通过并激活合同后，登记付款、交付或验收义务。
6. 后台定期检查履约时间，生成提醒、逾期风险和后续处理记录。
7. 审计人员根据请求或追踪标识，查询相关操作和异步处理过程。

这是一条用于验证系统能力的示例流程，不代表已经服务真实采购客户。

## 三、我的开发工作

在 ContractOps 部分，我围绕以下工作展开开发：

- **业务建模**：设计合同、合同版本、审批策略、审批实例、审批任务、履约义务和风险事件等模型。
- **接口与权限**：实现后端 API、JWT 鉴权、角色权限以及个人、部门、租户级数据范围控制。
- **业务一致性**：实现状态机约束、请求幂等、审批版本冲突检测和事务内事件记录。
- **异步处理**：实现文档解析、事件发布、通知消费、任务租约、失败重试和死信重放。
- **工程验证**：补充单元测试、数据库集成测试、迁移检查、性能回归和容器构建流程。
- **运行与交付**：提供本地容器配置、健康检查、结构化日志、指标、链路追踪及运行文档。

我的重点不是堆叠接口数量，而是让业务在重复请求、并发操作、进程中断和依赖故障下仍具有明确、可验证的行为。

## 四、核心功能

### 1. 合同台账与版本管理

支持合同编号、标题、合同类型、交易方、金额、币种、有效期和所属部门等信息的登记与查询。

合同文件以独立版本保存，修改文件时新增版本，而不是覆盖历史内容。文件记录包含内容摘要、大小和对象存储位置，为审批快照和版本差异分析提供依据。

### 2. 条件审批与任务流转

审批策略可以按合同类型、部门、金额区间及币种进行匹配，并为审批步骤设置所需角色和金额条件。

支持任务领取、转交、批准、驳回和要求修改。已发布的策略保持不可变，审批实例保存当时的策略快照，避免后续策略更新改变历史审批依据。

### 3. 文档解析与证据定位

支持 PDF 和 DOCX 文件的异步解析，保留页码或标题路径等定位信息。通过规则提取金额、日期等候选信息，并提供不同版本之间的证据差异查询。

上传采用“申请上传地址 → 上传文件 → 确认完成 → 后台解析”的方式。后台处理会校验文件大小和 SHA-256 摘要，并限制异常压缩文档等危险输入。

### 4. 履约义务与风险管理

支持付款、交付、验收、续约和终止通知等义务类型。每条义务记录负责人、到期时间、宽限期及完成证据。

调度器根据时间窗口生成提醒和风险记录，支持风险确认、延期与解决。合同终止时，关联的有效履约任务会被取消，避免继续产生不适当的提醒。

### 5. 多租户权限与审计

通过 JWT 识别租户、用户、角色和数据范围，在应用层执行访问控制，并在 PostgreSQL 层使用行级安全策略进行租户隔离。

业务操作、权限拒绝和后台处理具有审计记录。审计查询受到角色限制，日志采用字段白名单，避免直接记录令牌、密钥和合同正文。

## 五、技术架构

项目采用分层后端设计：API 层处理请求和鉴权，应用层组织用例，领域层定义业务状态和规则，基础设施层负责数据库、对象存储和消息通信。

| 技术 | 在项目中的用途 |
| --- | --- |
| Python / FastAPI / Pydantic | API 服务、请求校验与业务逻辑 |
| PostgreSQL / SQLAlchemy / psycopg | 业务持久化、事务、租户隔离和并发控制 |
| Alembic | 数据库版本迁移与升级验证 |
| Redis Streams | 异步事件传递、消费者组和消息恢复 |
| MinIO / S3 兼容接口 | 合同原始文件存储和临时上传地址 |
| OpenTelemetry / Prometheus | 链路追踪、运行指标与故障定位 |
| Docker Compose | 本地依赖与后端进程编排 |
| pytest / Ruff / mypy | 自动化测试、静态检查和类型检查 |
| Locust / GitHub Actions | 性能回归、持续集成与构建验证 |

运行进程分为 API、事件 Worker、文档 Worker 和履约 Scheduler。它们属于同一个项目中的职责拆分，不意味着已经建设了复杂的微服务平台。

## 六、重点技术设计与取舍

### 1. 应用权限与数据库隔离配合

仅在查询语句中手工添加租户条件，容易因遗漏而出现数据越权。我在应用权限检查之外增加 PostgreSQL 行级安全，并将租户上下文绑定到数据库事务。

API 运行身份受到租户隔离约束；需要跨租户扫描任务的 Worker 使用独立身份，并限制表权限。迁移身份与运行身份也分开使用。

### 2. 幂等与并发冲突分别处理

重复点击或网络重试，通过幂等键重放原有结果；同一个键携带不同请求内容时返回冲突。

多个审批人竞争同一任务时，则通过状态和版本校验拒绝陈旧操作。幂等解决“同一请求重复执行”，版本校验解决“不同请求同时修改”，两者不能互相替代。

### 3. 使用 Outbox 保证业务与事件一起落库

如果先提交数据库、再直接发送消息，进程可能在两步之间退出，造成业务成功但消息丢失。

因此，我把业务变更和 Outbox 事件写入同一个数据库事务，再由后台进程投递到 Redis Streams。通知侧结合投递记录、失败重试和死信重放，实现可恢复的异步处理。

这里不声称网络通知能够天然做到绝对的“仅投递一次”。接收端仍需要根据稳定的幂等键去重，以覆盖远端已接收、发送端尚未记录成功的时间窗口。

### 4. 用租约管理后台任务

后台任务通过数据库锁和租约进行领取，文档处理过程中持续续租。写回时校验任务归属、领取次数和有效租约，避免旧 Worker 在任务被接管之后覆盖新结果。

这种方式重点解决进程中断后的恢复与并发领取问题，而不是简单依赖“一个定时脚本永远不会退出”。

### 5. AI 只提供辅助建议

文档解析和规则提取可以在模型关闭时运行。可选模型输出需要经过证据校验，只保存为待人工确认的候选信息，不自动生成最终审批决定、履约义务或风险处置结论。

当前不将向量检索、扫描件 OCR、自动法律判断或自动签约列为已经完成的能力。

## 七、测试与验证

我通过自动化测试覆盖正常业务流程和异常路径，包括：

- 合同状态转换、审批策略、任务转交及陈旧版本冲突；
- 跨租户隔离、部门与个人数据范围，以及未授权访问；
- 重复请求、幂等键过期和后台清理；
- Worker 租约接管、消息失败恢复和通知去重；
- 履约调度、风险生成和终止后的任务取消；
- 文档解析、原文证据、版本差异和危险输入拒绝；
- 数据库迁移往返、运行角色权限和容器构建。

在本次文档编写前已核验的一次 CI 运行中，后端 **124 项测试全部通过**；该运行提供 PostgreSQL 和 Redis，未跳过相关集成测试。本机检查为 **107 项通过、17 项因缺少数据库和 Redis 环境而跳过**。

这些结果代表对应代码版本的回归验证，不等同于真实企业生产验收。性能测试目前用于 CI 基线回归，不据此宣称生产并发规模、用户数量或可用性指标。

## 八、当前交付边界

项目目前定位为**个人后端工程实践与本地面试展示项目**。

已具备核心业务后端、数据库迁移、异步任务、测试与持续集成，以及本地和生产环境的配置模板。当前电脑的完整本地演示环境仍需安装容器运行依赖并完成启动验收。

尚未将以下内容作为已交付成果：

- 完整的合同管理前端工作台与商业化 SaaS 产品；
- 真实企业上线、实际客户数量或线上业务收益；
- 电子签章、真实付款执行、企业单点登录与外部 ERP 对接；
- 生产环境容量验证、长期运行数据和备份恢复演练。

本地演示的下一步是准备测试租户、演示合同和角色身份，跑通上传、审批、履约、审计及故障恢复流程，并形成可重复操作的演示脚本。

## 九、面试中的一分钟介绍

> 我开发了一个叫 ContractOps 的企业合同审批与履约风险管理后端。它不只是管理合同文件，而是把合同建档、文档解析、条件审批、履约提醒和审计追溯串成一条业务流程。
>
> 技术上采用 Python 和 FastAPI，使用 PostgreSQL 保存业务数据，Redis Streams 处理异步事件，MinIO 保存合同文件。我重点设计了多租户隔离、请求幂等、审批并发控制，以及基于 Outbox 和任务租约的故障恢复机制。
>
> 这个项目目前用于本地演示和工程能力展示，没有包装成已经服务真实企业的线上产品。它最能体现的是我对业务状态、一致性、安全边界和异常恢复的理解。
